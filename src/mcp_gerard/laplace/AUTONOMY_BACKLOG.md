## Generating skills to forge-by-doing (mathematics & evidence)
The core of the generating activity ("doing mathematics to add to evidence") and the producers of the result schema's derivation, machine-map, and empirical faces. Identified this session but deliberately NOT forged: a generating skill is earned from the friction of actually doing the act, and no derivation or numerical check has been run yet. Forge each from real friction the first time the act is performed (the first core result of a project), never from imagination.
- **Derivation generation.** Doing the mathematics: declare the assumptions used, name and apply the technique, execute the steps to the result, and emit the compact machine-map (assumptions / techniques / recipe). Distinct from `epistemic_ledger` (evaluates derivation flow) and `result_foundry` (records the locked result) - neither does the deriving.
- **Numerical-evidence generation.** Writing and running the demonstration that validates an analytic result and yields the verdict for its status. Distinct from `empirical_ledger`, which audits existing data against claims after the fact - this produces the evidence in the first place.
- **Activity mislabel (related).** `empirical_ledger` is tagged `generating` but is an auditing / `evaluating` skill. Reclassify it; the mislabel helped hide the numerical-generation gap.

## Generation-stage rails - design targets
The generation stage is three peer staging rails (results / literature / numerics) - `result_foundry`'s four faces redistributed across peer owners. `result_foundry` exists; the other two rails were promoted to `staging` this session, but their storage and retrieval design is open. Each is forge-by-doing, earned after a project's core results are settled, never from imagination. Captured here so the design is not half-built in the protocols ahead of being attempted.
- **Shared literature corpus (cross-project store, not a per-project bib).** The literature rail must not be a per-project `references.bib`. Past failure mode: citations were ad hoc and ignored the literature actually accumulated across projects. Design one flexible, shared literature database - one store, many projects - so a common reference is gathered once, not re-gathered per paper. Per entry it should carry where-in-the-manuscript tags (intro / related work / discussion / ...) - a later-stage decision - so the right context surfaces for the section being drafted. The hard requirement on any design: literature is *easy context to surface while drafting*, and reliably reflects the whole accumulated corpus. `literature_scout` selects into this store rather than owning a copy. Relates to `deep_corpus_scout` (ingestion) above - the scout fills the store, this defines the store and its retrieval.
- **Figure faces are two, not one.** `numerical_evidence` covers only the simulation-data figure (the check plot). A paper's identity also needs schematic / explanatory figures and a hero figure - both belong at generation stage, not bolted on at drafting. Forge a figure skill (or split) by doing, once core results are done. The data-figure attaches to the numerics rail; the schematic and hero figures attach to the identity / spine rail. Relates to `aesthetics/visual_mechanics` and `aesthetics/tikz_guidelines`.

## Engine behaviour
- **orient under-ranks generating skills.** `laplace_orient` returns `skills.generating == []` even when the bucket is populated. Fix the relevance ranking so generating-activity skills surface for relevant goals.
- ~~**Canon hot-reload.**~~ *Done (2026-05-30):* `get_canon()` now caches against an mtime fingerprint over the manifest, lifecycle overlay, and skill/wiki sources, reloading automatically when anything changes on disk - so host-forge writes and hand edits are live without a fresh session. `fresh=True` still forces a reload.
- **Clean-context dreaming (top item).** The dreamer's generative step should run on distilled friction plus telemetry in an isolated context, never a long saturated session transcript - the engine's own context-firewall. Provide a way to hand the dreamer a scrubbed brief rather than a whole conversation.
- **Dreamer reads this backlog.** Wire the autonomous agenda to consult this file alongside the fitness assessment, so deferred items resurface on their own.
- **No-op dream orphans evidence (refines the done recency window).** *Floor guard done (2026-05-30):* `dream()` no longer stamps `dream_complete` on an idle fire - if no transition was applied, no forge brief was produced, and `events_seen < _NOOP_EVENT_FLOOR`, the boundary holds and `out["boundary_advanced"]` is `False` (test: `test_noop_dream_does_not_advance_boundary`). This fixes the observed failure (a dream over zero events fragmenting the window). *Remaining:* the split-friction case - friction arriving as a few events on each side of a non-idle dream, each window below an assess threshold so no single dream ever accumulates enough to act - needs the other option: scope deterministic curation to a longer rolling window than the forge brief, rather than the single since-last-dream cut.
- **orient-guard for domain=null (structural backing for `orient_recovery`).** When a bundle returns `domain=null`, emit the index summary and candidate domains inline with the bundle, so the `orient_recovery` recipe is handed to the model in the same response that triggers it - structural enforcement rather than remembered discipline. This is the named future backing in the forged skill.
- **Engine doc: kernel vs full routine.** The README should distinguish `laplace_dream` - the deterministic kernel (scoped assess + lifecycle transitions + a `host_forge` brief) - from the full R&R routine (the dreamer persona's end-of-session routine, run by `session_closer`). The kernel run alone is near no-op on feedback-only friction, since `assess` never demotes a `core` skill on negative feedback (it only flags `refine`), and the refine is host-executed. Users reasonably expect one "full autonomous dream" call; there is none by design - the depth is host-executed. State this so it is not rediscovered each session.
- **Deprecated skills are demoted but never swept.** The dreamer demotes on sustained non-use, but a `deprecated` skill stays on disk, in `index.yaml`, and in every orient bundle's `available_refs` list. Six sit there now (`css_forge`, `html_mechanic`, `web_deployment_mechanic`, `git_mechanic`, `shell_mechanic`, `laplace_release_mechanic`). They are the only part of the footprint that grows monotonically - orient content is budgeted by `rank_skills(limit=6)` / `rank_wiki(limit=4)`, but `available_refs` is an unbounded flat list that scales linearly with canon size. Add a sweep: a skill `deprecated` past N dream windows with zero usage is archived out of the active tree (moved, not deleted - reversible via canon git history) and dropped from `available_refs`. Footprint is trivial today (~107KB, 45 refs); the item is the mechanism, deferred until size earns it.

## Skill and canon refinements
- **context_firewall: sibling-project clause.** It covers canon-poisoning but not project-to-project poisoning. Encode the active re-earning firewall: prior material enters only by re-derivation, and names are earned once the development produces what they denote.
- **Author-layer accretion mechanism.** The author node was hand-placed. Give the dreamer a distinct global/author target, with cross-session recurrence gating so traits accrete slowly and are revised rather than frozen.
- **Fitness must not read silence as dissatisfaction.** The author under-vocalises praise (see `canon://author/the_author`), so explicit `laplace_log` feedback skews negative - corrections get logged, successes rarely do. `assess` should weight behavioural evidence (verify pass-rate, completed usage) above sparse explicit feedback, and never deprecate or down-rank a skill purely for an absence of positive signal. The compensating habit - self-logging behavioural +1s at session close - lives in `session_closer`; the assess weighting is the structural backstop.
- **Backing-script health.** *Exit-code honesty fixed (2026-05-30):* both evaluating scripts now exit 2 on an unreadable target and 0 on a produced report, so exec-ok means what assess assumes. Remaining: one evaluating skill still reports a low verify pass-rate; and the historical ok-rate-0.0 telemetry stays in the unbounded event log, so assess keeps surfacing a now-healthy skill - see "assess recency window" below.
- **run_backing discards failure diagnostics.** On a non-zero backing-script exit, telemetry records only `ok=false` - no returncode, no stderr tail. A later dreamer sees "script ok-rate 0.0" with nothing to act on and must re-reproduce by hand. Capture a short failure signature (returncode + stderr tail) on execute events so refine signals are self-diagnosing.
- ~~**assess recency window.**~~ *Done (2026-05-30):* `dream()` reads `last_dream_ts()` at the start of each cycle and scopes the assess call to events after that boundary. At the end of the cycle, `dream_complete` is stamped in telemetry so the next dream picks up the new boundary. `assess()` filters `dream_complete` events from its input so they never inflate fitness counts. History stays in the append-only JSONL for audit; it no longer pollutes measured fitness.
- ~~**Laplace test suite: 4 pre-existing failures.**~~ *Done (2026-05-30):* all four were stale assumptions, not engine breakage - `Skill.phase`→`activity`, flat-list vs activity-bucketed orient skills, and transition tests assuming pre-drift statuses. Fixed; the `isolated_canon` fixture now seeds a committed experimental baseline so promotion/deprecation are genuine and drift-proof. Suite green (21 passed), plus new hot-reload coverage.

## Architectural note
The autonomous dreamer's generative step is host-executed - the most powerful model already in the loop, running locally - not an external API call. Deterministic curation (fitness assessment, lifecycle transitions) stays in-engine. The engine stands as its own object.
